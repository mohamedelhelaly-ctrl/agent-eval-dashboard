# Agent Evaluation Dashboard: Project Plan

## 1. Task Description

Compare several versions of one AI agent on one job, using the same test questions and the same measurements, so that differences in results can be traced to what changed in the agent.

**The job:** a data analyst agent. It receives a natural-language business question (for example, "What was the churn rate in Q1 2025?"), explores a database, looks up business definitions, queries the data, and returns a single answer that can be checked automatically.

**What is held constant across all agent versions:** the task, the database, the tools, the glossary, and the eval set.

**What varies between agent versions:** the model and the prompt (see section 4). Only one of these is changed at a time against a baseline, so any change in results has one cause.

**Purpose of the evaluation:** show which agent version is best for a given balance of accuracy, cost, and speed, and where each version fails.

## 2. Dataset / Database Design

A synthetic SaaS company database in SQLite, generated by `generate_db.py` with a fixed seed (42) so it is identical on every run. "Today" for all questions is 2026-01-01, and the data covers 2023-01-01 to 2025-12-31.

### Tables

| Table | Key columns | Purpose |
|---|---|---|
| `customers` | customer_id, company_name, country, industry, signup_date, acquisition_channel, is_test_account | Who the customers are |
| `plans` | plan_id, plan_name, legacy_name, monthly_price, annual_price | Four tiers: Starter, Pro, Business, Enterprise |
| `subscriptions` | subscription_id, customer_id, plan_id, billing_cycle, start_date, end_date, status, cancel_reason | Each plan period for a customer |
| `invoices` | invoice_id, subscription_id, customer_id, invoice_date, amount, status, refunded_amount | Billing history |
| `support_tickets` | ticket_id, customer_id, created_at, resolved_at, priority, category, csat_score | Support activity |

### Size

| Table | Rows |
|---|---|
| customers | 500 (15 are test accounts) |
| plans | 4 |
| subscriptions | 697 |
| invoices | 5,878 |
| support_tickets | 1,500 |

### Planted edge cases

These separate careful agents from careless ones:

- **Re-subscribers:** customers who cancel and later return, which breaks naive churn counts.
- **Plan changes:** a plan change ends one subscription and starts another, so counting `status = 'cancelled'` overstates real cancellations.
- **Annual billing:** monthly recurring revenue requires dividing annual prices by 12.
- **Refunds and failed payments:** revenue totals change depending on whether they are included.
- **Test accounts:** internal customers flagged `is_test_account` that must be excluded from business metrics.
- **Renamed plan:** the Pro plan was formerly called "Growth" (stored in `legacy_name`), so a question using the old name needs a lookup.
- **Paused subscriptions:** a few ongoing subscriptions are paused and never count as active.
- **NULLs:** open-ended `end_date` and unrated `csat_score`, plus unresolved tickets.
- **Quarter-boundary dates:** subscriptions starting or ending exactly on dates such as Mar 31 and Apr 1.

### Glossary (business definitions the agent must look up)

`glossary.json` defines: active customer, MRR, churn rate, net revenue, ARPA, retention rate, and resolution time. It also states the conventions that apply everywhere:

- `end_date` is exclusive: it is the first day a subscription is no longer active.
- A subscription is active on date D if `start_date <= D`, `end_date` is NULL or after D, and status is not paused. Activity at past dates is decided by dates, not by the `status` column.
- Business metrics exclude test accounts.

## 3. Tools Provided for Each Model

Every agent version receives the same six tools. Only the model and prompt differ.

| Tool | What it does |
|---|---|
| `list_tables()` | Returns the tables in the database |
| `describe_table(table)` | Returns columns, types, and keys for one table |
| `sample_rows(table, n)` | Returns a few rows so the agent can see real formats and values |
| `run_sql(query)` | Executes a read-only SQL query and returns the results |
| `lookup_metric_definition(term)` | Returns the business definition of a term such as churn or MRR from the glossary |
| `calculate(expression)` | Does arithmetic that is awkward in SQL (percentages, growth rates) |

All tools are read-only, so nothing the agent does can change the data. The current date (2026-01-01) is given in the system prompt rather than through a tool, so relative phrases like "last quarter" resolve the same way on every run.

## 4. How the Agents Differ

One baseline agent is defined first. Each variant then changes exactly one thing from the baseline.

### Model

- Larger model vs smaller model
- Different providers

### Prompt

- Minimal instructions vs detailed instructions
- With examples vs without examples
- With an instruction to check the schema first vs without

## 5. Eval Metrics

Every agent version is scored on the same metrics. Each eval question is run several times per version, so results can be reported as averages and as consistency across runs.

| Metric | Definition |
|---|---|
| **Task completion rate** | Percentage of questions where the agent's final answer matches the expected value within a tolerance. Reported two ways: the average success rate across all runs, and the all-runs-pass rate (the share of questions answered correctly on every repeated run). |
| **Tool selection & call accuracy** | Two parts. Selection: the tools the question requires were called, and no unnecessary tools were called. Arguments: the SQL executed without errors and tool arguments were valid. |
| **Cost per successful task** | Total token cost across all runs divided by the number of successful runs, so failed runs count against the version. |
| **Latency (p50 and p95)** | Time from the question being sent to the final answer being returned, reported as the median and the 95th percentile rather than an average. |
| **Hallucination rate** | Share of unanswerable questions where the agent invents a number instead of saying the data cannot answer the question. |

## 6. Eval Set

A set of 30 to 40 natural-language questions about the database. Each question has an expected result and the tools a correct run should use.

### Fields for each question

| Field | Description |
|---|---|
| Question | The natural-language question given to the agent |
| Expected answer | The correct value, computed by running reference SQL against the database rather than by hand |
| Tolerance | How close the agent's answer must be to count as correct |
| Required tools | The tools a correct run must call (for example, the metric definition lookup for a question about churn) |
| Category tags | Used to break down results by question type |

### Example

| Field | Value |
|---|---|
| Question | What was the churn rate in Q1 2025? |
| Expected answer | 20 of 282 customers churned, about 7.1%, computed with the glossary's churn definition |
| Required tools | `lookup_metric_definition("churn")`, then `run_sql` |
| Tags | definition-dependent, time-based |

### Question categories

1. Simple lookups and counts
2. Joins and aggregations
3. Definition-dependent questions (the agent must look up the term, not guess)
4. Time-relative questions (for example "last quarter" or year over year)
5. Multi-step calculations (growth rates, ratios)
6. Unanswerable questions, where the correct behavior is saying the data does not contain the answer

Category 6 is what makes the hallucination rate measurable. The number of questions per category is still to be decided.
